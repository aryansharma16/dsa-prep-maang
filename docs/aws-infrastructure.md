# AWS infrastructure

What exists in AWS for this app, why each piece is shaped the way it is, and
which of its values the code actually reads. This is the inventory; the
operational side — deploying, verifying, fixing — lives in
[aws-runbook.md](./aws-runbook.md).

Everything below is in **account `580912381247`**, region **`ap-south-1`**
(Asia Pacific, Mumbai), except IAM, which is global.

---

## The short version

The application never holds an AWS credential. It runs on an EC2 instance that
carries an IAM role, and the AWS SDK's default credential provider chain reads
short-lived credentials for that role from the instance metadata service and
refreshes them before they expire. There is no access key to store, rotate or
leak, and no IAM user exists for this app.

The only two AWS settings the app reads are the region and the bucket name.

## Resources

### S3 bucket

| | |
|---|---|
| Name | `maang-prep-580912381247-ap-south-1-an` |
| Region | `ap-south-1` |
| Created | 10 August 2026 |
| Key prefix | `maang-prep/` (from `AWS_S3_PREFIX`) |

Every object the app writes lives under one prefix, so a shared bucket stays
sorted and `deletePrefix` can be scoped without guessing. The prefix is
applied by `keyFor()` in
[s3.service.js](../server/src/services/s3.service.js) — nothing lands at the
bucket root.

The bucket is private. Reads are served through short-lived signed URLs
generated by `signedGetUrl()`, so no object is publicly readable and the app
stays the only thing that can authorise a read. Objects are written with
`ServerSideEncryption: AES256`, which uses S3's own key and needs no KMS
permissions.

`AWS_S3_PUBLIC_URL` is deliberately unset. It is only for a bucket made public
or fronted by CloudFront; setting it makes `publicUrl()` return a permanent
link, and on a private bucket that link would look correct and 403 for every
visitor.

#### Access posture

| Setting | Value | |
|---|---|---|
| Block *all* public access | **On** | Nothing is reachable without a signed URL |
| Bucket policy | none | Access is granted entirely through the instance role's IAM policy |
| Object Ownership | Bucket owner enforced | ACLs disabled; every object is owned by this account |
| ACL grants to `AllUsers` / `AuthenticatedUsers` | none | |
| CORS | none | Correct — see below |
| Versioning | off | |
| Replication / Inventory | none | |
| Lifecycle rules | **none** | See [the multipart note](#incomplete-multipart-uploads-bill-forever) |

Granting access through the role's IAM policy and leaving the bucket policy
empty is the right split for a single-account app: one place to read, one place
to change, and no chance of the two disagreeing about who may write.

**CORS is empty and that is correct today.** Every asset is consumed by the
browser as an `<img src>` or an `<iframe src>` — see
[NoteBlocks.jsx:138](../client/src/components/notes/NoteBlocks.jsx#L138) — and
cross-origin image and iframe loads are not subject to CORS. Uploads go through
the API, not to S3 directly.

It stops being correct the moment either of these happens, and both are on the
table:

- the client `fetch()`es a signed URL rather than assigning it to `src`
  (a download button, a canvas read, a PDF fetched into a viewer), or
- uploads move to `signedPutUrl()` so the browser PUTs straight to S3 — which
  is the recommended answer to [the memory ceiling](#memory-ceiling).

Either needs a CORS rule allowing the app's origin. Reach for it then, not
before.

### IAM role

|---|---|
| Name | `MAANGPrepEC2S3Role` |
| Trusted entity | AWS service: `ec2` |

Attached to the instance below as its instance profile. This is the identity

### IAM policy `MAANGPrepNodeAppS3Access`

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "Objects",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::maang-prep-580912381247-ap-south-1-an/*"
    },
    {
      "Sid": "Bucket",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:ListBucketMultipartUploads"],
      "Resource": "arn:aws:s3:::maang-prep-580912381247-ap-south-1-an"
    }
  ]
}
```

Two statements, because S3 splits its permissions across two ARN shapes and
mixing them up is the usual cause of a deployment where uploads work and
listing does not:

- **Object actions** are granted on `bucket/*`. These cover the per-object
  calls: writing, reading, deleting.
- **Bucket actions** are granted on the bucket ARN with **no `/*`**.
  `s3:ListBucket` is a permission on the bucket itself, so a policy that grants
  it on `bucket/*` silently denies every `listObjects` and `deletePrefix` call
  while every upload continues to succeed.

The two multipart actions are not optional. `lib-storage`'s `Upload` switches
from a single PUT to a parallel multipart upload above the 5MB part size, so
every file over 5MB takes that path — which is most phone photos. A policy
without `s3:AbortMultipartUpload` and `s3:ListMultipartUploadParts` passes
every small-file test and then fails only on large files, which reads as an
intermittent bug rather than a permissions gap.

`s3:PutObjectAcl` is absent on purpose: the bucket uses bucket-owner-enforced
ownership, nothing sets a per-object ACL, and granting it would be permission
the app never uses.

The address is an Elastic IP rather than the instance's default public IP, so
it survives a stop/start and the GitHub Actions secret `EC2_HOST` does not need
updating after a reboot.

**IMDSv2 is required**, which is the right setting — it forces the
session-token handshake and blocks the SSRF-style attack where a tricked server
fetches `169.254.169.254` and hands back role credentials. The SDK speaks
IMDSv2 natively, so this costs nothing. One consequence to remember: the
default hop limit of 1 means a process inside a Docker container cannot reach
IMDS and the credential chain fails there. PM2 runs the app directly on the
host, so this does not apply today — but containerising would need the hop
limit raised to 2.

**1 GiB of RAM is the constraint worth keeping in view.** See
[Memory ceiling](#memory-ceiling) below.

Three settings are defaults that deserve a deliberate decision:

- **Termination protection is off** — see [the risk below](#the-instance-is-a-single-point-of-failure).
- **CPU credits are `unlimited`** — a `t3.micro` has a 10% CPU baseline and
  burst credits above it. In `unlimited` mode, sustained CPU past the baseline
  is billed as surcharge rather than throttled, so a runaway process or a busy
  spell shows up on the invoice instead of as slowness. That is often the right
  trade for a user-facing app, but it is an uncapped one. `standard` mode
  throttles instead of charging.
- **Detailed monitoring is disabled**, so CloudWatch collects at 5-minute
  granularity. More importantly, EC2 never reports **memory** at any
  granularity — it is invisible from outside the guest. Given the 1 GiB ceiling,
  an OOM kill currently leaves no trace except PM2's restart counter.

### Security group rules

| Rule ID | Port | Protocol | Source | Note |
|---|---|---|---|---|
| `sgr-091b312d0d0b3a7c4` | 22 | TCP | `0.0.0.0/0` | GitHub Actions |
| `sgr-099576c6a03c262e6` | 443 | TCP | `0.0.0.0/0` | |

Two things here are worth a deliberate decision rather than an accident:

**SSH is open to the entire internet.** The rule is labelled "GitHub Actions"
because the deploy workflow SSHes in, and GitHub's hosted runners come from a
large, rotating IP range — so pinning the source to a few addresses is not
straightforward. It is still port 22 reachable by anyone. The mitigations
worth considering, in rough order of effort: ensure password authentication is
disabled and only the deploy key works; restrict the source to
[GitHub's published Actions ranges](https://api.github.com/meta), refreshed on
a schedule; or move the deploy off SSH entirely onto AWS Systems Manager
Session Manager, which needs no inbound rule at all.

**There is no rule for port 80.** That is fine for serving traffic — HTTPS
only is the correct posture — but Let's Encrypt's HTTP-01 challenge renews
certificates over port 80. If TLS was set up with certbot's default flow,
renewal will fail silently when the certificate comes up for it. Either open
80, or switch that certificate to the DNS-01 challenge.

Nothing exposes the Node process's own port (`4000`) directly, which implies a
reverse proxy terminating TLS on 443 and forwarding locally. That proxy's
configuration is not currently captured in this repo.

## What the application reads

Only two variables, both in `server/.env` **on the instance**:

```bash
AWS_REGION=ap-south-1
AWS_S3_BUCKET=maang-prep-580912381247-ap-south-1-an
AWS_S3_PREFIX=maang-prep          # optional, defaults to maang-prep
```

There is deliberately **no** `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` or
`AWS_SESSION_TOKEN`, and adding them would be a downgrade rather than a
convenience — the chain checks environment variables *before* the instance
metadata service, so a stray static key silently shadows the role and
reintroduces exactly the long-lived secret the role exists to avoid.

`server/.env` is gitignored and **is not deployed by the pipeline**, which only
runs `git pull`. It is hand-maintained on the box. A new variable added to
`.env.example` therefore reaches production only when someone SSHes in and adds
it — this is the single most common way an otherwise-correct deploy fails.

### How credentials resolve

[`s3.service.js`](../server/src/services/s3.service.js) constructs its client
with a region and no `credentials` option:

```js
client = new S3Client({ region: env.s3.region, maxAttempts: 3 });
```

That omission *is* the credential strategy. Passing nothing makes the SDK run
its default provider chain, in this order:

1. Environment variables — `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`
2. SSO cache
3. `~/.aws/credentials` and `~/.aws/config`
4. **EC2 instance metadata service → `MAANGPrepEC2S3Role`** ← the production path

On the instance, steps 1–3 find nothing and step 4 succeeds. Resolved
credentials are temporary STS credentials whose access key ID begins `ASIA`,
and the SDK refreshes them automatically before expiry.

The client is built lazily, on first use, so importing the module never reaches
for a credential and the server boots normally whether or not S3 works.

### Why `configured` excludes credentials

`env.s3.configured` is `Boolean(region && bucket)` — it does not and cannot
test for a credential, because the deployment that matters has none to inspect.
Testing for one would disable uploads on exactly the box where they work. A
missing or misscoped role instead surfaces as a 502 on the first call carrying
the SDK's own message, which is the honest failure.

The trade-off is that a machine with region and bucket set but no credential
source — a developer laptop — reports storage as enabled and then fails at
request time. That is why `npm run s3:probe` exists.

## Local development

The same chain covers a laptop through steps 1–3, but this project does not
issue IAM user keys, so there is no static-key option. Choose one:

- **Use AWS IAM Identity Center (SSO)** — `aws sso login --profile <name>`,
  then `AWS_PROFILE=<name>` in `server/.env`. Credentials are short-lived, same
  as production. This is the recommended path.
- **Accept that attachments only work on EC2** — in which case remove
  `AWS_REGION` and `AWS_S3_BUCKET` from your *local* `server/.env`, so uploads
  fail fast with a clear 503 `STORAGE_DISABLED` instead of a confusing
  "Could not load credentials from any providers" after a full round trip.

## Constraints worth knowing

### The instance is a single point of failure

This is the highest-value item on the page, and the cheapest to fix.

`server/.env` exists **only** on this instance. It is gitignored, the deploy
pipeline never writes it, and no copy exists anywhere else. It holds the Mongo
connection string, both JWT secrets, every AI provider key and the S3 settings.

Meanwhile the instance has **termination protection disabled**, no EBS snapshot
policy, and is not in an Auto Scaling group. A mis-clicked *Terminate* in the
console — one menu item away from *Stop* — destroys the root volume and every
secret with it, permanently. Rebuilding means reissuing keys from four
different vendors' dashboards.

Three fixes, in order of value per minute spent:

1. **Enable termination protection.** EC2 → the instance → Actions → Instance
   settings → Change termination protection. Ten seconds, and it turns an
   irreversible mistake into a refused action.
2. **Back up `.env` somewhere durable.** A password manager entry is enough. It
   is the only artefact here that cannot be rebuilt from the repo.
3. **Enable an EBS snapshot lifecycle policy.** Data Lifecycle Manager, daily,
   7-day retention. Pennies per month for a t3.micro's root volume.

Longer term, moving the secrets into AWS Systems Manager Parameter Store
(SecureString) or Secrets Manager would let the instance read them at boot
through the same role that already reads S3, which removes the hand-maintained
file entirely and takes the "deploy forgot to update `.env`" failure mode with
it. That is a larger change and not urgent.

### Memory ceiling

The instance has **1 GiB of RAM** and uploads are buffered in the heap —
`multer.memoryStorage()`, chosen because bytes go straight back out to S3 and a
disk round trip would buy nothing.

The note-assets route
([note.routes.js:74](../server/src/routes/note.routes.js#L74)) accepts
`maxMb: 25, maxFiles: 10`, so the worst case for **one** request is:

| | |
|---|---|
| Multer buffers | 10 × 25MB = **250MB** |
| Multipart parts in flight | 4 files × 4 parts × 5MB = **80MB** |
| **Peak, one request** | **~330MB** |

Node's default heap on a 1 GiB host is roughly half of it. One maximal request
is survivable; two concurrent ones are not, and the process is OOM-killed and
restarted by PM2 mid-upload. For a single-user app this is unlikely to be hit,
but it is a real ceiling rather than a theoretical one.

The options, in increasing order of effort: lower the route's limits to
something like `maxMb: 10, maxFiles: 5`; add a swap file to absorb the spike;
or move large uploads to `signedPutUrls()`, which is already implemented and
never routes bytes through the server at all. The last is the right answer if
attachment sizes grow.

### HEIC is accepted by S3 and rejected by the upload filter

The two allowlists disagree:

- [s3.service.js:183](../server/src/services/s3.service.js#L183) includes
  `image/heic`, and `sniffType()` detects it from the ISO-BMFF brand.
- [upload.js:16](../server/src/middleware/upload.js#L16) does **not** include
  `image/heic`.

Multer's `fileFilter` runs first, so an iPhone photo in its default HEIC format
is rejected with a 400 `BAD_FILE_TYPE` and never reaches the code that would
have accepted it. Worth resolving one way or the other, and it matters here
because the attachments being uploaded are phone photos. Note that HEIC also
does not render in Chrome or Firefox, so accepting it end to end means
transcoding it to JPEG or WebP on the way in — which is the more likely correct
answer than simply adding it to the filter.

### Incomplete multipart uploads bill forever

Now that files over 5MB take the multipart path, an upload that fails partway
leaves parts in the bucket. They are invisible in the console's object list and
are billed as storage indefinitely.

The bucket has no lifecycle rule to clean them up. Add one — S3 Console →
bucket → Management → Lifecycle rules → *Delete expired object delete markers
or incomplete multipart uploads* → 7 days. It costs nothing and is the standard
companion to enabling multipart.

## Deployment

Pushes to `main` that touch `server/**` trigger
[.github/workflows/deploy-backend.yml](../.github/workflows/deploy-backend.yml),
which SSHes to the instance and runs:

```bash
cd ~/dsa-prep-maang && git pull origin main
cd server && npm ci
pm2 restart dsa-api --update-env && pm2 save
```

Required GitHub Actions secrets: `EC2_HOST`, `EC2_USER`, `EC2_SSH_KEY`.

Two consequences of this shape:

- **`server/.env` is never touched.** New configuration must be added to the
  box by hand. See [the runbook](./aws-runbook.md).
- **Client changes do not deploy the backend**, because of the `server/**` path
  filter. That is intended, but it means a change spanning both needs both
  paths pushed.

`npm ci` installs strictly from `package-lock.json` and fails outright if it
disagrees with `package.json`, so both must be committed together.
